# 项目讲解提纲

## 一句话介绍

我做的是一个面向客服质检和工单协作场景的多 Agent 系统，不是普通问答机器人。它会把一次客服处理拆成“理解问题、检索知识、生成回复、审核合规、总结沉淀”五个阶段。

## 你可以这样讲问题背景

传统客服机器人主要有两个问题：

- 只会回答，不会表达“为什么这样回答”
- 缺少审核和状态流转，容易在信息不足时直接输出结论

所以这个项目的重点不是单纯接一个大模型，而是把客服流程做成一个可追踪、可解释的 Agent 工作流。

## 你可以这样讲架构

### 1. 多 Agent 编排

- `IntakeAgent`：意图识别和风险判断
- `KnowledgeAgent`：FAQ / SOP / 历史经验召回
- `ResolutionAgent`：回复和处理建议生成
- `QAAgent`：做合规审查和质量把关
- `SummaryAgent`：产出摘要、标签和记忆沉淀

### 2. 状态机

我没有把它做成纯聊天，而是定义了明确的状态：

- `UNDERSTANDING`
- `RETRIEVING`
- `DRAFTING`
- `REVIEWING`
- `NEEDS_INFO`
- `READY_TO_SEND`
- `ESCALATED`

这样做的好处是能保证“追问、发送、建单、升级”这些动作彼此自洽。

### 3. 检索层

检索没有只做向量库，而是用了 Elasticsearch 双路召回：

- 向量召回解决语义匹配
- 关键词召回保证 FAQ / SOP 关键字段不丢

最后再融合排序，这样比纯向量检索更适合客服知识场景。

### 4. 数据层

- MySQL：会话、工单、AgentTask、QaAudit
- Redis：短期会话事件
- RabbitMQ：异步记忆沉淀
- Elasticsearch：知识库和长期记忆

## 你可以这样讲核心设计取舍

### 为什么不是单 Agent

如果只用一个 Agent，它既要理解问题，又要查知识，还要审核自己，职责容易混在一起。拆成多 Agent 后，我可以单独观察每一步的输出，也更方便在前端展示流程轨迹。

### 为什么一定要 QA Agent

客服场景很强调风险控制。很多系统能回答，但不会审核自己。我专门加 QA Agent，就是为了把“生成”和“审核”解耦，避免越权承诺或遗漏关键说明。

### 为什么需要状态机

我希望系统是任务流，而不是黑盒聊天。比如：

- 信息不足就进入 `NEEDS_INFO`
- 风险高或 QA 不放行就进入 `ESCALATED`
- 审核通过才进入 `READY_TO_SEND`

这样整个系统更像企业内部真实流程。

## 你可以这样讲你做了什么

- 设计了多 Agent 分工
- 设计了客服状态流转和建单规则
- 接入了 ES 双路召回
- 做了流程详情页，能展示状态、证据、Agent 执行和 QA 审核
- 补了最小测试和运行说明

## 面试官如果问“还有哪些不足”

可以坦诚说：

- 当前规则和模型输出仍有一定耦合，还可以继续做更强的规则引擎
- 前端现在是工作台原型，还没做更完整的运营视角报表
- 长期记忆的效果评估还可以继续补指标

这样回答会显得你既有工程落地能力，也知道项目下一步该往哪走。
